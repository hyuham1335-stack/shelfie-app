## 서술

### 문제

응답 미확인 사유 `unreadable` 한 칸이 기전 셋을 담았다 — 판독 확신도 미달 · 조회 상한(65)에 밀림 · 제목을 정규화하면 빈 문자열. 그중 '상한에 밀림'은 프롬프트 품질이 아니라 우리가 건 예산 정책의 결과인데, 미확인 비율 가드레일(20% 초과 → 추출 프롬프트 롤백)의 분자에 그대로 들어갔다. 책이 많은 세션이 곧 '프롬프트가 나빠졌다'로 읽혔고, 조회 상한이 80에서 65로 내려가며 그 겹침이 넓어졌다. `lookup_failed`를 분자에서 빼 두고 이것을 남긴 것은 같은 오독을 다른 문으로 들이는 일이었다.

### 원인

화면의 요구와 지표의 요구가 반대인데 한 어휘로 둘을 다 감당하려 했다. 사용자는 할 수 있는 일이 같으면 같은 문장을 봐야 하므로 사유를 잘게 쪼갤 이유가 없고, 지표는 원인을 갈라야 어디를 고칠지 알 수 있다. 그 둘을 한 enum 이 지고 있었다.

### 해결

계측 어휘를 응답 어휘의 세분으로 따로 두고 응답 사유를 거기서 유도한다. 계측 사유 일곱(`low_confidence`·`lookup_capped`·`blank_title`·`no_match`·`ambiguous`·`search_failed`·`facts_failed`)이 `RESPONSE_REASON` 으로 응답 사유 넷에 접힌다. 응답 enum·화면 매핑 넷·그 회귀 검사는 한 글자도 안 바뀌었다. 가드레일은 분자·분모를 같은 모집단으로 맞추고 계측에서만 `mergeKey` 로 중복을 접는다 — 응답 목록은 전부 그대로 보여준다.

### 결과

앱 테스트 1352 → 1403(+51). 게이트 두 번 다 통과하고 등급 `PASS_WITH_GAPS`. 리뷰어 지적 중 가장 값진 둘이 실제 반례를 들고 왔다 — 조회 상한에 밀린 후보를 분모에만 남기면 판정 실패율 30.8% 가 이벤트에서 10% 로 나오고, 알라딘 전면 장애 세션은 0% 로 가장 좋은 성적을 낸다. 둘 다 지금은 검사로 박혀 있다. 남은 한계 넷은 TRD 6.4 에 이름을 붙여 적었다.

### 배운 점

이 런에서 가장 값진 것은 코드가 아니라 **리뷰가 계획보다 나은 답을 낸 자리**다. 01-plan 은 저확신 중복 문제를 '고치면 미확인 카드가 화면에서 사라진다'며 범위 밖으로 뒀는데, 05 의 `data` 리뷰어가 '응답은 그대로 두고 계측에서만 접는다'는 길을 냈다. 계획이 대안을 다 세지 못했고 리뷰가 그것을 메웠다. 반대로 값비쌌던 것은 **내가 쓴 계약이 틀린 자리**다 — 분모를 분자보다 넓게 정해 Major 넷의 뿌리가 됐다. 계약이 지표를 정의할 때는 분자와 분모를 같은 문장에서 정의해야 한다.

### 계약이 어디서 부족했는가

계약이 세 번 부족했고 세 번 다 역할·리뷰어가 먼저 찾았다. ① 분모를 '확인 + 미확인 전부'로 정해 분자에서 뺀 셋을 분모에 남겼다 — `data` 가 `CONTRACT_DEFECT` 로 올렸고 이것이 Major 넷의 뿌리였다. ② `measureUnidentified` 의 인자를 하나로 적었는데 같은 절이 분모를 '분자 + 확인된 책 수'로 정했다 — 두 문장이 동시에 참일 수 없었고 `impl`·`test` 가 독립적으로 같은 자리를 짚어 같은 해석으로 풀었다. ③ 접힘의 대표를 정하지 않았다 — `test` 가 '어느 바구니가 이기는지 계약이 말하지 않아 검사를 쓰지 않았다'고 보고했다. 답을 지어내지 않고 비워 둔 것이 옳은 판단이었다. 그리고 계약 대조가 `## 유닛` 절만 파싱하므로 `## 데이터 형태` 에 적은 타입은 `out_of_contract` 로 잡힌다 — 첫 판에서 둘이 그렇게 걸렸다.

### 05 리뷰 범위가 적절했는가

라우팅이 `data`·`sec`·`arch` 셋을 골랐고 `test` 는 프로파일 상한 3 에 밀렸다. 셋 다 실제로 돌았고(3/3) 지적 11건을 냈다. diff 가 42,919바이트로 인라인 상한(25,000)을 넘어 **경로 전달 폴백**을 썼다 — 리뷰어가 직접 `git diff` 를 읽었다. 상한에 밀린 `test` 관점의 공백은 실제로 남았다: 지적 11 중 다섯이 `target_role: test` 였고 그것을 낸 것은 `data`·`arch` 다. 즉 테스트 품질을 본 것은 테스트 전문 리뷰어가 아니라 다른 관점의 리뷰어들이었다. 델타 재리뷰는 봉투가 지목한 `data` 한 명이 돌아 라운드 1 의 다섯을 전부 닫고 새로 다섯을 냈다.
