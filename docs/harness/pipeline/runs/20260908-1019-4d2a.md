## 서술

### 문제

미확인 비율 가드레일의 접힘 규칙이 두 자리에서 틀렸다. TRD 6.4 가 스스로 적어 둔 한계 넷 중 앞의 둘이다. ① 접힘이 확인/미확인 경계를 안 넘어, 같은 책의 흐릿한 판독본은 분자로 또렷한 판독본은 확인으로 가 한 책이 분자와 분모에 각각 1씩 들었다 — 열 권을 두 장에 담아 각각 흐릿+또렷을 내면 전부 확인된 세션인데도 50%로 읽힌다. ② mergeKey 가 증거가 없을 때도 값을 내, 정규화 제목이 빈 후보들이 전부 같은 키로 한 건에 접혔다 — 판독이 가장 나쁜 세션에서 분자가 가장 작게 나오는 뒤집힌 지표다. 뒤의 둘(③④)은 이 런의 범위 밖이다.

### 원인

둘 다 merge.ts:148 의 mergeKey 가 만든 문자열 하나를 어떻게 쓰느냐의 문제였다. ①은 그 키를 확인된 책 쪽에서 버려서(route.ts:222-235 가 identifiedFacts 를 조립할 때 안 실었다) 경계를 못 넘었고, ②는 그 키가 증거가 없을 때도 값을 내서 남을 잘못 접었다. 같은 리포의 match.ts:113 은 이미 반대로 판정해 두고 있었다 — '어느 한쪽이라도 정규화 결과가 비면 0을 돌려준다'. merge.ts:96 은 두 모듈이 어긋나지 않는다고 선언하는데 실제로는 어긋나 있었다. 선언과 코드가 갈린 자리이고, 이 리포가 반복해 잡아 온 형태다(ADR-H025).

### 해결

mergeKey 의 반환형을 string | null 로 바꿔 '접을 근거가 없음'을 1급으로 말하게 했다. 키 계산을 reduceBeforeLookup 한 곳으로 올리고 toLookup·capped 가 그 키를 나르게 해, 소비처가 다시 계산하지 않는다 — 덕분에 PromotedBook.mergeKey 가 string 인 채로 남고 좁히는 분기가 안 생겼다. 정규화 제목이 빈 후보는 조회 대상에서도 뺐다(blankTitle 바구니 신설) — 넣으면 65칸을 잠식해 읽히는 책을 lookup_capped 로 밀어내고, 그것이 요청이 ②에서 문제 삼은 것과 같은 형태다. 확인 키는 dedupeByIsbn 전의 promoted 에서 모아 identifiedFacts 의 ISBN 과 교집합해 넘겼다. 문서는 TRD 6.4 의 계측 어휘 표·모집단 경계·lookup_capped 감소 경로 표와 한계 목록을 갱신했고, API_SPEC 에는 응답 스키마 무변경과 미확인 카드 상한이 이미 있다는 판정 둘을 적었다.
